# Ревью setup и райсинга перед завершением проекта

Дата: 21 сентября 2026 года. Проверено состояние после раунда 15, коммит `1c86d46`.

Этот документ фиксирует результаты анализа и предложения. Перечисленные исправления по результатам ревью не применены.

## Общий вывод

Выбранный стек стоит сохранить и завершить проект одним проходом стабилизации. По быстродействию основа хорошая. Перед заморозкой остаются несколько конкретных ошибок и важная задача: сделать репозиторий полноценным источником текущего рабочего состояния.

В ходе ревью изучены документация, журнал изменений, установленные скрипты и конфигурации, запуск служб, расход ресурсов и сторонние реализации. Диагностические проверки многомониторной логики выполнены с подменёнными системными вызовами, без переключения экранов и изменения настроек.

`deskd` работает от событий. Частый опрос включается во время перетаскивания, а не постоянно. У сети два долгоживущих процесса ping, погода кэшируется, календарь использует GTK. Это хорошие решения. В замере Firefox также не показывал заметного давления памяти. Оснований переписывать всё на другой язык, менять оконный менеджер или снова переделывать управление памятью не найдено.

Существенного запаса «бесплатной» производительности не обнаружено. Основной результат следующего прохода — воспроизводимость, предсказуемые настройки и закрытые ошибки на границах сценариев. После этого проект можно переводить в обслуживание.

Первоначальный всплеск CPU `deskd` после перезапуска и при взаимодействии не подтвердился как постоянная нагрузка. В повторных пяти окнах измерения по пять секунд процесс показывал 0% CPU.

У picom во время использования рабочего стола наблюдалось примерно 3,8–7,2% одного ядра, у панели — 1–1,8%. Это не измерение полностью неподвижного рабочего стола и не доказательство избыточной нагрузки. Влияние отключения эффектов на энергопотребление не измерялось; обещать экономию батареи по этим данным нельзя.

## Находки по приоритету

### 1. Текущее состояние нельзя надёжно восстановить одним клонированием проекта

В Git 206 файлов, из них 165 — `.bak`. Основные действующие исходники `deskd`, календаря, панельных скриптов и конфигурации живут за пределами репозитория. Журнал объясняет, что менялось, но не содержит полного устанавливаемого результата.

Это главный незакрытый пункт перед сворачиванием проекта. Нужны:

- актуальные исходники и конфиги в репозитории;
- перечень зависимостей и управляемых настроек;
- проверка расхождений между репозиторием и установленной системой;
- воспроизводимый способ применения состояния.

Исторические бэкапы следует сохранить отдельным архивом вместе с журналом и его путями. Нельзя просто переместить или удалить их, оставив в журнале недействительные ссылки. Полезные тестовые сценарии также должны храниться в репозитории, а не только во временных каталогах сессий.

### 2. Механизм отката имеет реальные ограничения

Код: [lab/lab](lab/lab), функция `cmd_rollback`, строки 58–75 на момент ревью.

Откат старого эксперимента восстанавливает целый старый файл. Если позже тот же файл менялся ещё пять раз, эти изменения будут затёрты. Кроме того, строки удаляются из журнала даже при ошибке команды восстановления.

Ещё один дефект: имена резервных копий используют время с точностью до секунды, поэтому две записи одного файла в одну секунду могут столкнуться. Это место находится в `cmd_write`, строка 26.

Перед заморозкой следует:

- сохранять записи неудавшихся операций отката и возвращать ошибку;
- обеспечить уникальные имена резервных копий;
- запрещать выборочный откат для файлов с более поздними изменениями либо явно разрешать конфликт через сравнение версий;
- предусмотреть просмотр итогового diff перед будущими применениями.

Исторический журнал полезен для расследования изменений. Он сам по себе не заменяет описание желаемого текущего состояния и его установку.

### 3. Поддержка второго монитора разошлась с нынешней панелью

Код: установленный `~/.local/share/deskd/panels.py`, строки 123, 157 и 165–168.

Создание внешней панели ищет старый плагин `tasklist`. На основной панели уже `docklike`, поэтому вновь создаваемая внешняя панель остаётся без списка окон.

Проверка с подменёнными системными вызовами воспроизвела создание только этих плагинов:

```text
genmon → separator → separator → clock
```

Там же внешней полосе областей назначается Inter 10, тогда как основная использует Inter 15. Расчёт кликабельных зон в `deskd` берёт общий шрифт, поэтому появляется расхождение между изображением и геометрией. Шрифт нужно учитывать для конкретной панели либо явно поддерживать единый размер на всех панелях.

Ещё один воспроизведённый случай: полноэкранное окно на первом мониторе скрывает отметку активной области на втором. Причина — `break` в `sync_active_mark` установленного `~/.local/share/deskd/deskd.py`, строка 1872: обход прекращается до обработки второго экрана.

Это небольшие исправления, которые стоит закончить до объявления состояния стабильным. Физическое подключение и отключение HP всё ещё требует отдельной проверки; проверки с подменой вызовов её не заменяют.

### 4. Содержательная оптимизация сетевого индикатора

Код: установленный `~/.local/bin/netqd`, `Link.refresh`, строка 124.

Каждые 10 секунд выполняется `nmcli dev wifi`. Этот вызов может запускать сканирование эфира: по документации NetworkManager он обновляет список, если данные старше 30 секунд.

Для фонового индикатора достаточно `wifi list --rescan no`, а свежий уровень сигнала уже отдельно получается через `iw`. Это уберёт ненужную причину сканирований. Получение свежего списка сетей при открытии меню можно оставить отдельным действием.

В `net-menu` комментарий также обещает отсутствие сканирования, хотя соответствующий вызов `nmcli` явно не указывает `--rescan no`; поведение и комментарий нужно согласовать.

Влияние на задержку и расход батареи здесь ещё не измерено, поэтому конкретных процентов выигрыша обещать нельзя.

Источник: [документация NetworkManager, nmcli](https://networkmanager.pages.freedesktop.org/NetworkManager/NetworkManager/nmcli.html).

### 5. Запуск служб стоит привести к завершённому состоянию

У `~/.config/systemd/user/deskd.service` настроены бесконечные рестарты каждую секунду: `StartLimitIntervalSec=0`, `Restart=always`, `RestartSec=1`. При ошибке запуска служба будет повторять её без ограничения.

Нужны ограничение частоты, корректная привязка к графической сессии и использование импортированного окружения вместо жёсткого `DISPLAY=:0`. При изменении политики рестарта необходимо сохранить предусмотренное восстановление после перезапуска i3.

В `/usr/local/bin/xfce-i3-session`, строка 20, остался прямой запуск `nm-applet`, хотя его уже заменил `netqd`.

Более аккуратное распределение служб между `session.slice` и `background.slice` соответствует рекомендациям systemd. При этом в самодельной сессии нужно действительно управлять запуском и остановкой графического target: одного добавления зависимостей в unit-файлы недостаточно. Это улучшение управления жизненным циклом, а не обещание ускорения.

Источник: [Desktop Environment Integration, systemd](https://systemd.io/DESKTOP_ENVIRONMENTS/).

### 6. Не хватает общего источника оформления и сохранённых проверок

Цвета и размеры повторяются в i3, `deskd`, OSD, rofi, календаре и индикаторах. В конфиге i3 есть комментарий о необходимости совпадения цветов с `deskd`. Уже найденное расхождение шрифтов показывает практическую цену такого устройства.

Следует вынести палитру, типографику, размеры и интервалы обновления в один небольшой набор параметров. Конфиги могут генерироваться при применении; постоянный дополнительный демон для этого не нужен.

Своего кода уже около 6000 строк, из них примерно 2200 в `deskd.py`. Полная перепись не требуется. Полезно отделить геометрию и состояние окон от рисования и интеграции с панелью, сохранив единые обработчики команд.

В репозитории нужны проверки сложных сценариев:

- восстановление окна после разворота и изменения соседних контейнеров;
- создание и удаление панели второго монитора;
- fullscreen на одном экране при работе на другом;
- совпадение изображения полосы областей с зонами клика и перетаскивания;
- границы числовых индикаторов: переходы 9/10, 99/100, 999/1000;
- повторяющиеся события календаря;
- открытие путей, перенесённых терминалом на следующую строку.

Сейчас описания проверок есть, а устойчивого набора тестов в проекте нет. Проверки чистой логики можно запускать без графической сессии; для оконного поведения полезен сохранённый сценарий во вложенном X-сервере.

У Regolith есть развиваемая документация и отдельные компоненты. Его подход к настройкам подходит как ориентир для этого проекта. Текущие требования к мыши, панели задач, восстановлению окон и мониторам существенно конкретнее обычных dotfiles, поэтому копирование чужой сборки не обещает улучшения.

Событийная интеграция `deskd` через IPC соответствует предусмотренной архитектуре i3. В существующем клиенте команды и подписка используют отдельные соединения, что согласуется с предупреждением официальной документации о смешивании ответов и событий: [i3 IPC](https://i3wm.org/docs/ipc.html).

## Хранение и применение будущих настроек

Предпочтительный готовый инструмент — **chezmoi с небольшой обвязкой для `xfconf` и системных файлов**. Он предоставляет сравнение, предварительный просмотр и шаблоны, запускается только по необходимости. На момент исследования у проекта около 21,7 тысячи звёзд и развитая документация.

Источники: [репозиторий chezmoi](https://github.com/twpayne/chezmoi), [модель применения](https://www.chezmoi.io/quick-start/), [размещение source state в подкаталоге](https://www.chezmoi.io/user-guide/advanced/customize-your-source-directory/).

Все применения в этом проекте должны по-прежнему проходить через журналируемый путь. Внедрение менеджера dotfiles само по себе не отменяет правило `lab/lab` и не должно создавать незаписанные изменения.

Нужно явно разделить:

- управляемые исходники и настройки;
- параметры конкретной машины, пользователя и мониторов;
- изменяемое состояние программ и кэш;
- внешние учётные данные.

Нельзя бездумно превращать весь XML XFCE с историей устройств и внутренними идентификаторами в универсальный шаблон. Для изменяемых каналов нужны выбранные управляемые свойства и определённый порядок применения. Персональные пути и координаты погоды должны стать параметрами, а не частью общего кода.

## План кристаллизации

1. Зафиксировать действующие исходники, конфиги и зависимости; сверить их с установленной системой.
2. Исправить найденные ошибки отката, второго монитора, автозапуска и фонового сканирования Wi-Fi.
3. Сделать одну команду проверки состояния и воспроизводимые проверки основных сценариев.
4. Сжать документацию до трёх документов: текущее устройство, правила оформления и поведения, обслуживание и восстановление. Старые планы и подробный журнал оставить историей.
5. После проверки входа в сессию, сна и пробуждения, внешнего монитора поставить стабильный тег.

Документация уже требует согласования: [STATE.md](STATE.md) в заголовке говорит о раунде 9, хотя включает более поздние изменения; [RICING.md](RICING.md), [REVIEW.md](REVIEW.md) и часть [lab/README.md](lab/README.md) описывают прежнее состояние.

Для завершения нужен конечный проверяемый результат: репозиторий содержит актуальную реализацию, команда сравнения не показывает необъяснённых расхождений, основные сценарии проверены, а будущая смена настроек не требует поиска дублирующихся констант.

## Краткие правила оформления и поведения

- Чёрная основа; `#0d8ecb` для структурных акцентов, `#48daf9` для светящихся индикаторов; остальные цвета обозначают состояние.
- Inter для интерфейса, моноширинные цифры для показателей, DSEG для часов.
- Фиксированная геометрия во всех состояниях; рисование и зоны клика используют одни размеры.
- Клавиши, мышь и жесты вызывают общие команды.
- Настройки применяются сразу и сохраняются; персональные параметры отделены от кода.
- Фоновые компоненты работают от событий, внешние данные кэшируются, отсутствие сети обрабатывается спокойно.
- Новая функция получает место в системе при понятной пользе и приемлемой измеренной цене.
- Пользовательские надписи — на английском; проверки окон выполняются во вложенной сессии или предусмотренными средствами просмотра, без лишнего вмешательства в рабочий экран.

## Необязательная доводка и уборка


Из уборки полезны устранение устаревшего автозапуска, исключение сгенерированных `.pyc` из Git и удаление ненужных debug-пакетов. На момент проверки среди orphan-пакетов были `mbpfan-debug`, `vesktop-bin-debug`, `xkb-switch-debug` и `cmake`. Последний не следует удалять только по этому признаку: машина используется для разработки.

Чистка кэшей при свободных примерно 177 ГБ не даст заметного ускорения. Изменения compositor ради экономии батареи имеет смысл рассматривать только после сопоставимых измерений. Данных, обосновывающих смену рабочего стола или большую перепись собственных компонентов, это ревью не дало.
