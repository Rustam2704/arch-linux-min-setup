# KWin floating-window mechanics on Plasma 6 X11

Scope: KDE **kwin-x11 Plasma/6.7**, commit `b3ac4f9` (2026-09-09). KDE [split the X11 window manager into its own repository](https://mail.kde.org/pipermail/plasma-devel/2025-March/123654.html) for Plasma 6.4. This branch builds the standalone `kwin_x11` executable (`src/CMakeLists.txt:kwin_x11`). Every source pointer below refers to this commit at `https://invent.kde.org/plasma/kwin-x11/-/tree/b3ac4f9`. Defaults mean KWin's compiled configuration defaults, before user settings or window rules. KWin still has shared X11/Wayland window logic, but X11-specific claims below point to its X11 path. Pixel distances are KWin logical coordinates unless stated otherwise. A source comment is not treated as behaviour where executable code differs from it.

## 1. Stacking of transients and modal dialogs

- KWin keeps an unconstrained user stacking order, then sorts it by layer and applies parent-below-transient constraints to produce the actual order. An ordinary `WM_TRANSIENT_FOR` relationship calls `Window::addTransient`, which adds a stacking constraint; `Workspace::constrainedStackingOrder` moves a transient above its parent even if an ordinary raise/lower operation would put it below. `Workspace::propagateWindows` sends that calculated order to X and `_NET_CLIENT_LIST_STACKING`. Sources: `src/window.cpp:Window::addTransient`, `src/layers.cpp:Workspace::constrainedStackingOrder`, `src/layers.cpp:Workspace::propagateWindows`.
- The constraint has exceptions. A splash is not constrained above a parent that is itself a dialog; a **nonmodal group transient dialog** is not forced above every group member; and a transient of a dock is normally not forced above that dock unless it carries a transient placement hint. These are explicit tests, not a general exemption for frameless windows. Source: `src/window.cpp:shouldKeepTransientAbove`.
- `WM_TRANSIENT_FOR = root` means group transient. KWin's `X11Window::groupTransient` tests that root ID. It treats a group transient as transient for earlier members of its X11 window group, removes relationships that would create cycles, and preferentially orders later group transients above earlier ones. Invalid self references, loops, or references to unmapped parents can be rewritten to root; splash windows without a parent are made group transient. Sources: `src/x11window.h:X11Window::groupTransient`, `src/x11window.cpp:X11Window::checkGroupTransients`, `src/x11window.cpp:X11Window::verifyTransientFor`, `src/x11window.cpp:X11Window::checkGroup`.
- Clicking/activating a main window with a modal descendant does not focus the blocked main window. `Workspace::takeActivity` finds the modal, keeps it on the main window's desktops, raises the originally targeted main if raising was requested, and redirects focus to the modal. `Window::findModal` searches transient descendants recursively. Thus a click can still bring the parent/modal stack forward, while keyboard focus lands on the dialog. Sources: `src/activation.cpp:Workspace::takeActivity`, `src/window.cpp:Window::findModal`.
- A frameless overlay covering an entire screen has **no special layer simply because of its dimensions or absent frame**. If it is a managed transient, its relationship and EWMH type determine the constraint/layer. If it is override-redirect, it is unmanaged and KWin's X stacking keeps unmanaged popups above managed frames. A Telegram-specific fullscreen-size overlay rule was not found. Sources: `src/window.cpp:Window::belongsToLayer`, `src/window.cpp:Window::addTransient`, `src/layers.cpp:Workspace::propagateWindows`, `src/x11window.cpp:SUPPORTED_UNMANAGED_WINDOW_TYPES_MASK`.
- Bottom-to-top `Layer` values in this branch are Desktop, Below, Normal, Above, Notification, Active, Popup, CriticalNotification, OnScreenDisplay, Overlay. There is no separate `DockLayer` in the enum despite an obsolete comment in `layers.cpp`: docks and applet popups map to Above. Splash maps to Normal; ordinary normal/dialog/utility windows generally map to Normal; keep-below to Below and keep-above to Above; regular notifications to Notification; critical notifications and OSDs higher. Unmanaged/internal windows use Overlay. `Window::belongsToLayer` gives these tests their order, so an active fullscreen takes Active before `keepAbove` is considered. Sources: `src/effect/globals.h:Layer`, `src/window.cpp:Window::belongsToLayer`.
- `Window::isActiveFullScreen` retains the Active layer when the fullscreen window is active, when the active window is on another output, or when the active window has that fullscreen window as a main window. A different active window on the **same** output makes the fullscreen window lose Active and fall back to its ordinary layer. KWin also promotes X11 group members on that output to Active when one group member is Active, then enforces transient constraints. Sources: `src/window.cpp:Window::isActiveFullScreen`, `src/layers.cpp:layerForWindow`, `src/window.cpp:Window::setActive`.

## 2. Focus stealing prevention

- The level enum is 0 None, 1 Low, 2 Medium, 3 High, 4 Extreme. This branch's `kwin.kcfg` sets the **compiled default to 1 (Low)**, even though an older comment inside `allowWindowActivation` calls level 2 the default. None permits activation; Low accepts uncertain requests more often; Medium rejects unknown timestamps; High normally allows only the active application or an unoccupied desktop; Extreme rejects unsolicited activation. Per-window rules can override the requester's focus-stealing prevention and the active window's focus protection. Sources: `src/kwin.kcfg:FocusStealingPreventionLevel`, `src/x11window.cpp:X11Window::allowWindowActivation`, `src/rules.h:checkFSP`, `src/rules.h:checkFPP`.
- KWin records `_NET_WM_USER_TIME`, user-time-window/group timestamps, startup-notification time, and a creation-time fallback for new X11 windows. It compares the requester's effective user time with the currently active window's time using `NET::timestampCompare`, which handles X timestamp wraparound. Time zero is an explicit request not to focus unless a rule overrides it. A missing time (`-1U`) is accepted at Low when the active window has less than High protection; Medium generally rejects it. Sources: `src/x11window.cpp:X11Window::readUserTimeMapTimestamp`, `src/x11window.cpp:X11Window::userTime`, `src/x11window.cpp:X11Window::allowWindowActivation`, `src/x11window.cpp:X11Window::updateUserTime`.
- On `_NET_ACTIVE_WINDOW`, source indication `1` (`FromApplication`) goes through `allowWindowActivation`; a rejected request sets demands-attention instead of activating. Source indication `2` (`FromTool`, pager/taskbar) force-activates, as do unknown source values normalized to `FromTool` here. If the app includes a valid currently active window ID, KWin has a second activation check for the transfer case. A zero request timestamp falls back to the target's user time. Source: `src/netinfo.cpp:RootInfo::changeActiveWindow`.
- New X11 windows also run the activation decision during `manage`; an unsuccessful attempt can request attention while leaving current focus intact. A rogue X11 `FocusIn` is checked too: KWin tries to restore its previous focus and then marks the offender as demanding attention. The attention state is exported as `_NET_WM_STATE_DEMANDS_ATTENTION`, and activation clears it. Sources: `src/x11window.cpp:X11Window::manage`, `src/events.cpp:X11Window::focusInEvent`, `src/x11window.cpp:X11Window::doSetDemandsAttention`, `src/window.cpp:Window::demandAttention`, `src/activation.cpp:Workspace::setActiveWindow`.

## 3. Focus after a window closes or minimizes

- On removal or minimizing an active X11 client, KWin calls `Workspace::activateNextWindow`. It ignores the operation if the removed client was neither active nor pending focus, and closes any active popup before selecting a successor. `X11Window::doMinimize` calls this before visibility is changed; removal does so on the close path. Sources: `src/x11window.cpp:X11Window::doMinimize`, `src/workspace.cpp:Workspace::removeX11Window`, `src/activation.cpp:Workspace::activateNextWindow`.
- Under the default Click to Focus policy, with `NextFocusPrefersMouse=false`, the order is: preserve Show Desktop by focusing its desktop window if active; optionally select a visible window under the pointer if that option is enabled; if the closing/minimizing window is a transient with exactly one usable main window, focus and raise that main window; otherwise select the most recently active usable window from the current desktop's `FocusChain`; finally focus the desktop or null focus. The main-window preference is conditional, not universal. Sources: `src/kwin.kcfg:FocusPolicy`, `src/kwin.kcfg:NextFocusPrefersMouse`, `src/activation.cpp:Workspace::activateNextWindow`, `src/focuschain.cpp:FocusChain::nextForDesktop`.
- `FocusChain` maintains a chain per virtual desktop plus a global most-recently-used chain. Focus activation moves a window to the end of the per-desktop chain, and successor selection scans that end first. Candidates must be shown, on the current desktop/activity, and, because `SeparateScreenFocus=true` by default, on the relevant output. Hidden/minimized windows do not win immediate focus. Sources: `src/focuschain.cpp:FocusChain::update`, `src/focuschain.cpp:FocusChain::nextForDesktop`, `src/focuschain.cpp:FocusChain::isUsableFocusCandidate`, `src/kwin.kcfg:SeparateScreenFocus`.
- Focus Follows Mouse, Focus Under Mouse, and Strictly Under Mouse are available but have different takeover behaviour. `activateNextWindow` avoids the usual fallback if `focusPolicyIsReasonable()` is false; the pointer/enter path then governs focus. The default is Click to Focus. Sources: `src/options.h:FocusPolicy`, `src/options.h:focusPolicyIsReasonable`, `src/activation.cpp:Workspace::activateNextWindow`, `src/kwin.kcfg:FocusPolicy`.

## 4. Placement of new windows

- The selectable placement policies are Random, Smart, Centered, ZeroCornered, UnderMouse, OnMainWindow, and Maximizing; None/Default/Unknown are internal values. **Cascade is not a global policy** in this branch: `cascadeIfCovering` is a helper used by Random, Centered, and ZeroCornered to avoid fully covering an existing window. With decorations built, the default is **Centered**; a no-decoration build chooses Maximizing. Sources: `src/options.h:PlacementPolicy`, `src/kwin.kcfg:Placement`, `src/placement.cpp:Placement::place`, `src/placement.cpp:Placement::cascadeIfCovering`.
- Smart placement scans candidate x/y positions against visible windows on the target desktop/activity and chooses zero overlap if possible, otherwise the least weighted overlap. Overlap with keep-above windows costs 16 times more; keep-below non-dock windows contribute zero. Random is a deterministic stepping scheme, 24 pixels horizontally and 48 vertically; ZeroCornered starts at the placement area's top-left. Centered calculates the centered coordinate and then may cascade it to avoid full cover. Sources: `src/placement.cpp:Placement::placeSmart`, `src/placement.cpp:Placement::placeAtRandom`, `src/placement.cpp:Placement::placeZeroCornered`, `src/placement.cpp:Placement::placeCentered`.
- Dialogs use `placeOnMainWindow`: one suitable parent means center over that parent's **frame**, then `keepInArea` clips it into the work area on the parent's output. No parent, a desktop parent, or multiple current-desktop parents means center in the selected placement area. Splash uses the same main-window path. Utility placement currently delegates back to the default policy; its adjacent-to-parent algorithm is a TODO, not implemented. Sources: `src/placement.cpp:Placement::placeDialog`, `src/placement.cpp:Placement::placeOnMainWindow`, `src/placement.cpp:Placement::placeUtility`, `src/placement.cpp:Placement::place`.
- On X11, KWin does **not** simply center every dialog. `X11Window::manage` checks whether `WM_NORMAL_HINTS` has USPosition or PPosition; for most normal windows and many NETWM dialogs it accepts that requested position, unless a rule says Ignore Geometry. Non-dialog transients generally keep app position too, which matters for overlays and call windows. Splash usually follows KWin placement. The code rejects obviously far-off requested coordinates and runs `keepInArea` for movable ordinary windows; explicit position rules deliberately permit less confinement. Sources: `src/x11window.cpp:X11Window::manage`, `src/utils/xcbutils.h:GeometryHints`, `src/window.cpp:Window::keepInArea`.
- A new window's initial placement output comes from startup notification's Xinerama screen if supplied, otherwise `Workspace::activeOutput`, then a window rule may replace it. `activeOutput` is updated by window activation and user pointer actions; X11 window activation can set it to the focused window's output. Therefore it is **not a fixed rule of mouse screen only or focused screen only**. For a dialog centered on a parent, placement re-evaluates the work area at the parent's center. Sources: `src/x11window.cpp:X11Window::manage`, `src/activation.cpp:Workspace::takeActivity`, `src/workspace.cpp:Workspace::setActiveOutput`, `src/placement.cpp:Placement::placeOnMainWindow`.

## 5. Maximize and restore

- `geometryRestore` stores the pre-maximize frame rectangle. `X11Window::maximize` saves only dimensions that are not already maximized, so switching between vertical, horizontal, and full maximization does not overwrite the unavailable dimension with a maximized size. MaximizeVertical stretches to work-area top/bottom while keeping the normal width; MaximizeHorizontal stretches left/right while keeping normal height; MaximizeFull fills `MaximizeArea`. A missing restore dimension triggers constrained fallback sizing and smart placement. Sources: `src/x11window.cpp:X11Window::maximize`, `src/window.cpp:Window::geometryRestore`, `src/workspace.cpp:Workspace::clientArea`.
- A title-bar drag from maximized state starts as a move. As soon as the move would change a maximized axis, KWin calls `maximize(MaximizeRestore)`. In its interactive-move branch, restoration uses `anchor - (saved width × interactiveMoveOffset.x, saved height × interactiveMoveOffset.y)`. The offset was measured as the pointer's fractional position inside the original frame at press, so the same **proportional grab point** remains under the pointer. The quick-tile drag-off path uses that same normalized offset. Sources: `src/window.cpp:Window::updateInteractiveMoveResize`, `src/x11window.cpp:X11Window::maximize`, `src/window.cpp:Window::requestTile`, `src/window.cpp:Window::processDecorationButtonPress`.
- A title-bar double click defaults to Maximize, normally a toggle through `Workspace::performWindowOperation`. Left/right border double click can toggle horizontal maximization, top/bottom border vertical, and corners full, with `DoubleClickBorderToMaximize=true` by default. The maximum button has distinct default left/middle/right actions: full, vertical, horizontal. Sources: `src/kwin.kcfg:TitlebarDoubleClickCommand`, `src/kwin.kcfg:DoubleClickBorderToMaximize`, `src/window.cpp:Window::processDecorationButtonPress`, `src/useractions.cpp:Workspace::performWindowOperation`.
- An app request to add/remove `_NET_WM_STATE_MAXIMIZED_VERT` or `_HORIZ` reaches `WinInfo::changeState`, which preserves an unaffected axis, calls `setMaximize`, and then `X11Window::maximize` checks window rules and size capability. During initial management, KWin also reads both state bits and applies them after geometry/placement. While maximized, ordinary client configure requests are generally prevented from overriding the user's maximized geometry. Sources: `src/netinfo.cpp:WinInfo::changeState`, `src/x11window.cpp:X11Window::manage`, `src/x11window.cpp:X11Window::maximize`, `src/x11window.cpp:X11Window::configureRequest`.

## 6. Quick tiling and edge snapping

- Dragging the pointer within **20 logical pixels** of a left/right work-area edge proposes a half tile. If its y-coordinate falls in the upper/lower **25%** of the work area (configurable `ElectricBorderCornerRatio=0.25`), the proposal becomes a quarter tile. Within **5 pixels** of the top edge, where no left/right tile is selected, the proposal is full maximize. Edge tiling and edge maximize are enabled by default. `Window::checkQuickTilingMaximizationZones` does these tests. Sources: `src/window.cpp:Window::checkQuickTilingMaximizationZones`, `src/kwin.kcfg:ElectricBorderTiling`, `src/kwin.kcfg:ElectricBorderMaximize`, `src/kwin.kcfg:ElectricBorderCornerRatio`.
- At an outer edge the proposal activates immediately. At an inner edge shared with another monitor, KWin delays activation by **250 ms** to reduce accidental tiling while crossing outputs. `setElectricBorderMaximizing` displays an `Outline` of the proposed tile or maximize rectangle; release commits that mode, hides the outline, and remembers the old geometry. The generic desktop-switching screen-edge delay is a different option, default **75 ms**, and should not be confused with the 250 ms quick-tile delay. Sources: `src/window.cpp:Window::checkQuickTilingMaximizationZones`, `src/window.cpp:Window::setElectricBorderMaximizing`, `src/window.cpp:Window::finishInteractiveMoveResize`, `src/screenedge.cpp:ScreenEdges::reconfigure`, `src/kwin.kcfg:ElectricBorderDelay`.
- `Meta+Left/Right/Up/Down` are default quick-tile shortcuts. Directions combine: Left then Up gives top-left; reversing an axis changes side. When a shortcut repeats the current tile side and a neighbouring output exists in that direction, KWin moves the tile to that output and flips the side facing back toward the old output (for example Left on the right monitor, then Left again, produces Right on the left monitor). If no neighbouring output exists, the same tile request is effectively unchanged; the nearby source comment about toggling off is stale. Sources: `src/useractions.cpp:Workspace::initShortcuts`, `src/window.cpp:combineQuickTileMode`, `src/window.cpp:Window::handleQuickTileShortcut`, `src/window.cpp:Window::requestTile`.
- Dragging a tiled window away calls `setQuickTileModeAtCurrentPosition(None)`, restoring saved `geometryRestore` with the pointer's fractional grab offset. A resize from an unsupported tile edge also exits that tile; a supported tile boundary may resize the tile tree. On output/work-area changes, `ensureSpecialStateGeometry` recomputes a tiled rectangle from the current tile geometry, rather than leaving fixed old pixels. Sources: `src/window.cpp:Window::updateInteractiveMoveResize`, `src/window.cpp:Window::requestTile`, `src/window.cpp:Window::ensureSpecialStateGeometry`, `src/window.cpp:Window::checkWorkspacePosition`.

## 7. Magnetic snapping while moving or resizing

- Defaults are **Border snap zone 10**, **Window snap zone 10**, **Center snap zone 0**, and **Only when overlapping false**. All are logical pixels and configurable. `adjustWindowPosition` scales thresholds by `snapAdjust`; ordinary interactive movement passes 1.0. KWin chooses the nearest eligible correction independently for x and y, so a border or neighbouring window only wins if closer than a previous candidate. Sources: `src/kwin.kcfg:BorderSnapZone`, `src/kwin.kcfg:WindowSnapZone`, `src/kwin.kcfg:CenterSnapZone`, `src/kwin.kcfg:SnapOnlyWhenOverlapping`, `src/workspace.cpp:Workspace::adjustWindowPosition`.
- The border target is `MaximizeArea`, not the raw display edge, so a panel strut changes the magnetic boundary. Window targets are visible windows on the current desktop/activity; KWin filters out desktop, dock, splash, notification, OSD, and unmanaged windows. A window edge can snap to another's opposing edge where their orthogonal spans overlap. Once one axis is aligned, corner tests can align the other axis. With Only when overlapping enabled, KWin only performs an edge snap after crossing the target edge rather than when merely near it. Sources: `src/workspace.cpp:canSnap`, `src/workspace.cpp:Workspace::adjustWindowPosition`, `src/workspace.cpp:Workspace::clientArea`.
- Center snapping, if enabled, requires both center-coordinate differences to be within the zone and each correction to beat its current competitor. It also enhances border snaps by aligning the other axis to the work-area center. During resize, `Workspace::adjustWindowSize` applies analogous border/window snapping to the moving edge selected by resize gravity; KWin then reapplies client size constraints. Maximized axes get larger border guidance zones so slight motion does not instantly break maximization. Sources: `src/workspace.cpp:Workspace::adjustWindowPosition`, `src/workspace.cpp:Workspace::adjustWindowSize`, `src/window.cpp:Window::nextInteractiveResizeGeometry`.

## 8. Interactive move and resize

- On the standalone X11 backend, `X11Window::doStartInteractiveMoveResize` attempts an asynchronous `xcb_grab_pointer` on KWin's frame with button, motion and enter/leave events. If that fails it tries a keyboard grab; at least one grab is required. `leaveInteractiveMoveResize` releases them. X11 motion events reach `X11Window::motionNotifyEvent`, which calls `Window::updateInteractiveMoveResize`. This differs from KWin's Wayland input-filter path. Sources: `src/x11window.cpp:X11Window::doStartInteractiveMoveResize`, `src/x11window.cpp:X11Window::leaveInteractiveMoveResize`, `src/events.cpp:X11Window::motionNotifyEvent`.
- A title-bar press starts a delayed move timer using Qt's `startDragTime`; sufficient pointer travel (`startDragDistance`) starts it sooner. Mouse movement is live: each changed move rectangle calls `move`; each changed resize rectangle calls `doInteractiveResizeSync`, except while awaiting an XSync acknowledgement. There is no separate wireframe-only move path in these functions. The code thus displays window content while moving and resizing, subject to an unresponsive client's redraw rate. Sources: `src/window.cpp:Window::startDelayedInteractiveMoveResize`, `src/events.cpp:X11Window::motionNotifyEvent`, `src/window.cpp:Window::updateInteractiveMoveResize`.
- When a client advertises `_NET_WM_SYNC_REQUEST_COUNTER`, KWin sends `_NET_WM_SYNC_REQUEST` and tracks one pending resize at a time. It waits for the client's counter acknowledgement before sending another interactive resize, preventing resize requests from outrunning the client; a timeout disables sync temporarily and allows progress. The branch uses 10 seconds once ready for painting and 1 second during initial setup. Without XSync, it applies the geometry directly. This is **resize pacing**, not a fixed rate limit on every pointer motion. Sources: `src/x11window.cpp:X11Window::getSyncCounter`, `src/x11window.cpp:X11Window::sendSyncRequest`, `src/x11window.cpp:X11Window::doInteractiveResizeSync`, `src/x11window.cpp:X11Window::ackSyncTimeout`.
- Unrestricted move/resize commands can let the frame go farther offscreen. Normal move uses `confineInteractiveMove` to keep a title-bar-visible subrectangle on an output and out of reserved struts. It requests **100 pixels of title-bar length** (capped by the actual frame width) and the current title-bar border thickness as its visible height. A frameless window has zero title-bar thickness, so this branch does not guarantee a 50-pixel visible strip for it. The region algorithm finds the nearest permitted frame position across multiple output rectangles. Sources: `src/window.cpp:Window::titlebarThickness`, `src/window.cpp:confineInteractiveMove`, `src/window.cpp:interactiveMoveResizeVisibleSubrectRegion`, `src/window.cpp:Window::nextInteractiveMoveGeometry`.
- The global mouse modifier defaults to **Meta**, configurable to Alt. Meta+left button defaults to activate/raise/move; Meta+right to activate/raise/resize, with the resize edge/corner picked from which third of the frame was clicked; Meta+middle toggles raise/lower. The ordinary inactive-window body click defaults to activate, pass click, and raise on release. Sources: `src/kwin.kcfg:CommandAllKey`, `src/kwin.kcfg:CommandAll1`, `src/kwin.kcfg:CommandAll3`, `src/window.cpp:Window::performMousePressCommand`, `src/options.cpp:Options::reparseConfiguration`.

## 9. Fullscreen windows and panels

- `WinInfo::changeState` accepts `_NET_WM_STATE_FULLSCREEN` changes and calls `X11Window::setFullScreen`, subject to fullscreen capability and window rules. Entering saves `fullscreenGeometryRestore`, clears shade, raises the window, sets the EWMH state, removes/updates its decoration and moves it to `FullScreenArea`. `_NET_WM_FULLSCREEN_MONITORS` can select a union of monitor rectangles; leaving restores the saved geometry. Sources: `src/netinfo.cpp:WinInfo::changeState`, `src/x11window.cpp:X11Window::setFullScreen`, `src/x11window.cpp:X11Window::updateFullscreenMonitors`.
- `FullScreenArea` is the raw output rectangle, while `MaximizeArea` and `PlacementArea` subtract panel struts. Thus a fullscreen window covers a panel's reserved area. The panel remains an Above-layer dock; the active fullscreen is in Active above it. Activating a different window on the same output removes fullscreen's Active status, allowing the new window and panel to be visible above it according to their layers. A fullscreen window on another output can remain Active on its own output. Sources: `src/workspace.cpp:Workspace::clientArea`, `src/window.cpp:Window::belongsToLayer`, `src/window.cpp:Window::isActiveFullScreen`, `src/activation.cpp:Workspace::setActiveWindow`.
- Notifications normally sit below active fullscreen. Critical notifications and OSDs sit above it, enabling volume/brightness feedback over video. KWin can block ordinary screen-edge activation while a fullscreen window covers the edge. It does not need to actually hide or unmap the panel to let fullscreen cover it; stacking and separate work/fullscreen areas explain the visible behaviour. Sources: `src/effect/globals.h:Layer`, `src/window.cpp:Window::belongsToLayer`, `src/screenedge.cpp:Edge::checkBlocking`, `src/layers.cpp:Workspace::constrainedStackingOrder`.

## 10. Alt+Tab

- Default Windows tab-box config uses the focus chain, only the current virtual desktop and activity, all applications, all monitors, and **includes minimized windows**. The alternative config uses all desktops. A window must also want tab focus and not request skip-switcher; a main window with a modal dialog is replaced by that modal where appropriate. Sources: `src/tabbox/tabbox.cpp:TabBox::TabBox`, `src/tabbox/tabbox.cpp:TabBoxHandlerImpl::clientToAddToList`, `src/tabbox/tabbox.cpp:TabBoxHandlerImpl::checkMinimized`, `src/tabbox/clientmodel.cpp:ClientModel::createFocusChainClientList`.
- The first item is the active window, and moving forward chooses the next most recently used candidate. `FocusChain` maintains this history separately from X stacking. Default shortcuts include Alt+Tab and Meta+Tab, with shifted reverse shortcuts; the tab box grabs the keyboard while cycling. Sources: `src/focuschain.cpp:FocusChain::firstMostRecentlyUsed`, `src/focuschain.cpp:FocusChain::nextMostRecentlyUsed`, `src/tabbox/tabbox.cpp:TabBox::initShortcuts`, `src/tabbox/tabbox.cpp:TabBox::establishTabBoxGrab`.
- The UI has a **90 ms delayed show** default. One press/release within that delay still changes the selected item and activates it on modifier release, commonly switching to the previous window without flashing a full switcher. Releasing the activating modifier accepts even if Tab remains held. A shortcut configured without held modifiers takes an immediate one-step route. Sources: `src/kwin.kcfg:DelayTime`, `src/tabbox/tabbox.cpp:TabBox::startKDEWalkThroughWindows`, `src/tabbox/tabbox.cpp:TabBox::delayedShow`, `src/tabbox/tabbox.cpp:TabBox::modifiersReleased`, `src/tabbox/tabbox.cpp:TabBox::KDEOneStepThroughWindows`.
- The default `HighlightWindows=true` previews the selected window through KWin effects, while activation/raising happens at accept. The highlight effect changes opacity of nonselected windows, rather than making every selection a permanent focus-chain or X stack change. The default tab-box UI and outline are enabled, subject to the active theme/effect implementation. Sources: `src/kwin.kcfg:HighlightWindows`, `src/tabbox/tabboxhandler.cpp:TabBoxHandlerPrivate::updateHighlightWindows`, `src/tabbox/tabbox.cpp:TabBoxHandlerImpl::highlightWindows`, `src/plugins/highlightwindow/highlightwindow.cpp:HighlightWindowEffect::highlightWindows`, `src/tabbox/tabbox.cpp:TabBox::accept`.

## 11. Minimize and restore

- Minimize is state, not movement to an offscreen coordinate. `X11Window::doMinimize` moves focus away if needed, updates X visibility, and propagates minimization to relevant transients. `updateVisibility` sets `_NET_WM_STATE_HIDDEN` and calls `internalHide`; unminimizing clears Hidden and shows/keeps the client according to desktop and activity visibility. Sources: `src/x11window.cpp:X11Window::doMinimize`, `src/x11window.cpp:X11Window::updateVisibility`, `src/window.cpp:Window::setMinimized`.
- Minimizing a main window also minimizes its nonmodal transients. Modal dialogs are excluded from that direct child pass, but minimizing a modal dialog minimizes its main window; unminimizing recurses through transients and main-window relations. This avoids an orphaned dialog or auxiliary window in common cases. Sources: `src/workspace.cpp:Workspace::updateMinimizedOfTransients`.
- User activation of a minimized window (`Workspace::activateWindow`) raises it, switches to its virtual desktop/activity according to policy, clears minimized and hidden states, and requests focus. The default desktop policy is SwitchToOtherDesktop. If a modal descendant blocks it, `takeActivity` sends focus to the modal instead. Simply setting minimized false is a visibility change; the explicit activation path is what restores front/focus semantics. Sources: `src/activation.cpp:Workspace::activateWindow`, `src/activation.cpp:Workspace::takeActivity`, `src/kwin.kcfg:ActivationDesktopPolicy`.
- Minimized windows remain in the global focus chain for Alt+Tab, but `FocusChain::nextForDesktop` requires `isShown`, so they are skipped as immediate focus-after-close candidates. Their X frames are not positioned at a special taskbar slot; taskbar icons may receive `_NET_WM_ICON_GEOMETRY`, which KWin uses for animation origin when present. Sources: `src/focuschain.cpp:FocusChain::nextForDesktop`, `src/tabbox/tabbox.cpp:TabBoxHandlerImpl::checkMinimized`, `src/x11window.cpp:X11Window::iconGeometry`.

## 12. Multiple monitors

- `Window::sendToOutput` translates a normal window by preserving its center's **fractional displacement from the old work-area center**: multiply each offset by the ratio of new-to-old work-area size, add the new center, and keep it inside if it was fully inside before. This is proportional placement, not a fixed pixel offset. It moves fullscreen and maximize restore rectangles through the same transform and sends transient descendants to the new output. Sources: `src/window.cpp:Window::moveToArea`, `src/window.cpp:Window::sendToOutput`.
- Maximized, fullscreen and quick-tiled windows are then passed through `ensureSpecialStateGeometry`: fullscreen fills the new output, each maximized axis fills the new work area, and quick tiling uses the new output's tile geometry. This prevents a maximized/tiled window from retaining the old monitor's dimensions. Sources: `src/window.cpp:Window::sendToOutput`, `src/window.cpp:Window::ensureSpecialStateGeometry`, `src/window.cpp:Window::quickTileGeometry`.
- When outputs change, `Workspace::updateOutputs` migrates quick tiles from a removed output to a surviving output and releases custom tiles. `Workspace::desktopResized` and `Window::checkWorkspacePosition` bring surviving normal windows back toward visible screens and recompute special-state geometry. `PlacementTracker` remembers geometry, output UUID, maximize/tile/fullscreen state, and restore rectangles for display-layout configurations; when a familiar layout returns it restores windows unless their interaction/state indicates the user changed them meanwhile. Sources: `src/workspace.cpp:Workspace::updateOutputs`, `src/workspace.cpp:Workspace::desktopResized`, `src/window.cpp:Window::checkWorkspacePosition`, `src/placementtracker.cpp:PlacementTracker::restore`.
- A display unplug is therefore not handled by assigning every window a single origin. There are separate paths for quick tiles, custom tiles, maximized/fullscreen windows, and normal frames; new-window placement still uses the active output/startup output rule described in section 4. On X11 the update code notes spurious output-change events and avoids cancelling a move for every such event. Sources: `src/workspace.cpp:Workspace::updateOutputs`, `src/x11window.cpp:X11Window::manage`.

## 13. Telegram-like overlays, calls, and special window types

- No Telegram Desktop-specific class, role, or media-viewer workaround was found in this KWin branch (`src/` and `data/` search for `Telegram` and `telegram`). Behaviour comes from generic X11 hints and user window rules. A frameless viewer that sets `WM_TRANSIENT_FOR` to the main window receives the normal transient relationship and, unless it identifies as a dialog/utility/splash with different placement, typically keeps its app-specified position. Its large geometry alone does not make it fullscreen; `_NET_WM_STATE_FULLSCREEN` is the separate fullscreen mechanism. Sources: `src/x11window.cpp:X11Window::manage`, `src/x11window.cpp:X11Window::setTransient`, `src/x11window.cpp:X11Window::setFullScreen`, `src/window.cpp:Window::belongsToLayer`.
- The managed EWMH types include Normal, Desktop, Dock, Toolbar, Menu, Dialog, TopMenu, Utility, Splash, Notification, OnScreenDisplay, CriticalNotification and AppletPopup. Override-redirect popup/dropdown/tooltip/combobox windows are ordinarily unmanaged. A legacy type-Unknown window with `WM_TRANSIENT_FOR` is treated as a dialog for compatibility. Sources: `src/x11window.cpp:SUPPORTED_MANAGED_WINDOW_TYPES_MASK`, `src/x11window.cpp:SUPPORTED_UNMANAGED_WINDOW_TYPES_MASK`, `src/x11window.cpp:X11Window::windowType`.
- Splash windows get Normal layer, parent/group transiency, main-window placement, and generally no ordinary focus. Utility windows follow default placement; their proposed parent-relative right-side placement is explicitly unimplemented. Notifications use their own high layer and on-screen placement rather than normal-dialog focus. OSDs sit still higher. Sources: `src/window.cpp:Window::belongsToLayer`, `src/placement.cpp:Placement::place`, `src/placement.cpp:Placement::placeUtility`, `src/activation.cpp:Workspace::takeActivity`.
- User window rules can match class/name (`WM_CLASS`), role (`WM_WINDOW_ROLE`), title, and window type, then constrain position, size, maximize/fullscreen, keep-above, no border, skip switcher/taskbar, output, and focus-stealing behaviour. For a media viewer or call window, class **plus role/type** is more targeted than class alone (inference). KWin reads a rule's Ignore Geometry before honouring position hints, and checks explicit Position before keeping the frame inside the ordinary work area. Sources: `src/rules.cpp:Rules::match`, `src/rules.cpp:WindowRules::checkPositionSafe`, `src/rulesettings.kcfg:wmclass`, `src/x11window.cpp:X11Window::manage`.

## 14. Other concrete floating-window refinements

- **Click delivery and focus are separate.** The default inactive body click can activate and pass the click to the app, then raise on release; title-bar clicks have their own active/inactive bindings. This reduces lost first clicks while still making the clicked window active. Sources: `src/kwin.kcfg:CommandWindow1`, `src/window.cpp:Window::getMousePressCommand`, `src/window.cpp:Window::performMousePressCommand`, `src/window.cpp:Window::performMouseReleaseCommand`.
- **Visibility is desktop/activity aware.** X11 `updateVisibility` distinguishes minimized/hidden windows from those merely on another desktop or activity (`internalHide` versus `internalKeep`), preserving state for compositing and switchers. Activation can bring a window to the current desktop or switch to its desktop according to `ActivationDesktopPolicy`. Sources: `src/x11window.cpp:X11Window::updateVisibility`, `src/activation.cpp:Workspace::activateWindow`.
- **Panel struts are geometry inputs.** A dock's `_NET_WM_STRUT_PARTIAL` changes per-output placement and maximize areas. Resized desktop/work-area geometry triggers position checks, while fullscreen deliberately uses raw output geometry. That keeps normal floating windows clear of panels without special hard-coded panel heights. Sources: `src/x11window.cpp:X11Window::strut`, `src/x11window.cpp:X11Window::strutRect`, `src/workspace.cpp:Workspace::adjustClientArea`, `src/workspace.cpp:Workspace::clientArea`.
- **Hints constrain client size.** KWin reads `WM_NORMAL_HINTS`, including min/max/base size, increments, aspect ratio, gravity, and explicit position. Interactive resize runs the proposed rectangle through snapping and client size constraints; initial placement happens after frame decorations and size hints have been applied. Sources: `src/utils/xcbutils.h:GeometryHints`, `src/window.cpp:Window::nextInteractiveResizeGeometry`, `src/x11window.cpp:X11Window::manage`.
- **Restoring geometry survives state transitions.** KWin keeps distinct normal/maximize and fullscreen restore rectangles, and `PlacementTracker` also stores them per output arrangement. Cancelling a move/resize restores the initial rectangle, maximization state, quick-tile state, and original output. Sources: `src/window.cpp:Window::finishInteractiveMoveResize`, `src/window.cpp:Window::setGeometryRestore`, `src/window.cpp:Window::setFullscreenGeometryRestore`, `src/placementtracker.cpp:PlacementTracker::dataForWindow`.
- **Placement and stacking are intentionally different decisions.** A dialog may be centered on a parent but still accept a program-specified X11 position; transiency can constrain its stacking independently. A nonmodal group dialog is even exempt from an always-above constraint. An i3-based layer needs to evaluate X11 type, transient, modality, geometry hints, and user rules separately to reproduce these outcomes. Sources: `src/x11window.cpp:X11Window::manage`, `src/window.cpp:shouldKeepTransientAbove`, `src/placement.cpp:Placement::placeOnMainWindow`, `src/layers.cpp:Workspace::constrainedStackingOrder`.
- **Unresponsive clients do not freeze interactive resize forever.** XSync waits for redraw acknowledgement but has a fallback timeout that disables sync temporarily. X11 move itself does not require client repaint to update frame position. Sources: `src/x11window.cpp:X11Window::sendSyncRequest`, `src/x11window.cpp:X11Window::ackSyncTimeout`, `src/x11window.cpp:X11Window::doInteractiveResizeSync`, `src/window.cpp:Window::updateInteractiveMoveResize`.
- **Attention is a fallback to focus stealing.** Failed activation is surfaced through demands-attention rather than silently disappearing, while a successful activation clears it. This also covers a transient that appears for a minimized parent. Sources: `src/netinfo.cpp:RootInfo::changeActiveWindow`, `src/x11window.cpp:X11Window::manage`, `src/activation.cpp:Workspace::setActiveWindow`, `src/window.cpp:Window::demandAttention`.
